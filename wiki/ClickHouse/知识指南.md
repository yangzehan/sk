# ClickHouse 升级与 ZooKeeper 到 Keeper 迁移知识文档

> 本文档记录 ClickHouse 22.2 → 23.8 升级及 ZooKeeper → Keeper 迁移的完整知识体系，包括架构原理、排错指南、最佳实践。
> 适用于运维工程师参考，不依赖任何外部系统。

---

## 一、架构基础

### 1.1 ClickHouse ReplicatedMergeTree 工作原理

ClickHouse 副本同步依赖 ZooKeeper（现为 Keeper）：

```
写入流程：
1. 写入 shard1-replica1 (leader)
2. 在本地完成写入，生成 part
3. 通过 Keeper 记录 part 元数据（path, size, hash）
4. 其他副本从 Keeper 读取元数据，发现新 part，拉取数据

副本选择逻辑：
- 写入时自动选择任意一个健康副本作为 leader
- Keeper 协调谁负责哪个 part 的同步
- 如果一个副本落后，它会从 Keeper 获取需要同步的 queue

Keeper（ZK）存储的关键数据：
/clickhouse/tables/<uuid>/<shard>/replicas/<name>/   ← 每副本状态
/clickhouse/tables/<uuid>/<shard>/parts/<name>        ← 每个 part 的元数据
/clickhouse/task_queue/                                 ← DDL/Mutation 队列
```

### 1.2 ZooKeeper 与 ClickHouse Keeper 的区别

| 维度 | ZooKeeper | ClickHouse Keeper |
|------|-----------|-------------------|
| 开发方 | Apache ZK 官方 | ClickHouse 自己实现 |
| 协议兼容 | 原始 ZK 协议 | ZK 兼容协议（ClickHouse 自行实现） |
| 配置方式 | zoo.cfg | keeper_config.xml |
| 数据迁移 | 无需迁移 | `clickhouse keeper-converter` |
| 性能 | 一般 | 优化过，QPS 更高 |
| 运维 | Java 依赖（JDK） | C++，无额外依赖 |
| 配置兼容性 | - | 与 ZK 100% 兼容，CK 无感知 |

### 1.3 clickhouse-keeper-converter 详解

**核心作用**：将 ZooKeeper 的 snapshot + log 文件转换为 Keeper 可以直接加载的 snapshot。

**调用方式**（重要！）：
```bash
# 错误方式 - 会报错 config 不存在
clickhouse-keeper-converter ...

# 正确方式 - clickhouse 主程序的子命令
clickhouse keeper-converter ...
```

**为什么 `clickhouse-keeper-converter` 是错误入口？**
- 它是 `clickhouse-keeper` 的符号链接
- 运行时会尝试加载 `keeper_config.xml`
- 它本身不是独立的转换程序，而是 Keeper server 的一个子模式

**转换原理**：
```
ZK snapshot (snapshot.*) + ZK log (log.*)
    ↓ clickhouse keeper-converter
Keeper snapshot (snapshot_ZXID.bin.zstd)
```

**转换时 ZK 必须停止的原因**：
- ZK 运行时会持续写入新的 log 文件
- 如果 ZK 在运行，转换出来的 snapshot 可能缺少最新事务
- Keeper 需要从 snapshot + changelog 中恢复完整状态

## 二、升级与迁移流程详解

### 2.1 阶段一：ClickHouse 升级（22.2 → 23.8）

**为什么必须先升级 CK 再迁移 Keeper？**
- CK 22.2 与 Keeper 23.8 可能存在协议兼容性差异
- 先升级 CK 到 23.8，保证 CK 端稳定
- Keeper 迁移如果失败，只需回退 Keeper 配置，不影响 CK

**升级步骤关键点**：

```
1. STOP MERGES → 停止所有 merge，避免升级期间新 part 生成
2. clickhouse-backup create → 通过硬链接 freeze 数据，不额外占磁盘
3. 停止 CK
4. 升级 RPM（23.8）
5. 启动 CK
6. 验证版本 + 副本状态
7. START MERGES
```

**compress_marks / compress_primary_key 配置**：
- 22.2 默认开启，23.8 默认关闭
- 如果 22.2 数据开启了这些设置，23.8 无法读取
- 因此必须 `<compress_marks>false</compress_marks>` 在升级前写入配置

### 2.2 阶段二：Keeper 部署与 ZK 迁移

**Keeper 配置中的 `<zookeeper>` 段落**：

这是一个常见误解。Keeper 配置中的 `<zookeeper>` 段不是用于从 ZK 导入数据，而是用于：
- 让 Keeper 作为 ZK 的代理（fallback）
- 当 Keeper 无法处理某个请求时，代理到真实 ZK
- **迁移完成后应该删除**，避免依赖旧 ZK

**正确迁移流程**：
```
1. 6 台 CK 停机
2. 3 台 ZK 停止
3. .41 上运行 clickhouse keeper-converter（离线转换）
4. scp snapshot 到 .42 .43
5. 修改 keeper_config.xml（仅 raft 配置，无 <zookeeper> 段）
6. 启动 Keeper（.41 leader, .42/.43 follower）
7. 修改 6 台 CK metrika.xml（2181 → 9181）
8. 重启 6 台 CK
9. 验证
```

## 三、排错指南

### 3.1 常见错误及解决方案

#### 错误 1：is_readonly=1 且 last_queue_update_exception 为空

**原因**：Keeper 连接正常，但某个 part 在 Keeper 中没有注册，导致副本认为数据不同步。

**解决**：
```sql
-- 在本地节点检查
ALTER TABLE <db>.<table> DETACH PART '<part_name>';
-- 如果 DETACH 失败，说明 part 不存在，直接忽略

-- 在有数据的节点上 SYSTEM RESTART REPLICA
SYSTEM RESTART REPLICA <db>.<table>;
```

#### 错误 2：is_readonly=1 且 last_queue_update_exception 包含 "Connection refused 2181"

**原因**：CK 仍连接旧 ZooKeeper 2181，ZK 已停止。

**排查**：
```bash
# 1. 检查 metrika.xml 是否已修改
grep "2181\|9181" /etc/clickhouse-server/metrika.xml

# 2. 检查 config.xml 是否误改了
grep "zookeeper" /etc/clickhouse-server/config.xml | grep -v "<!--"

# 3. 重启 CK 确认加载最新配置
systemctl restart clickhouse-server
```

#### 错误 3：Keeper 所有节点都是 follower，无法选主

**原因**：网络不通，raft 节点间无法通信。

**排查**：
```bash
# 检查 raft 端口是否通
for h in 15.28.140.41 15.28.140.42 15.28.140.43; do
    timeout 3 nc -vz $h 9234 && echo "$h:9234 OK" || echo "$h:9234 FAIL"
done

# 检查 Keeper 日志
tail -30 /var/log/clickhouse-keeper/clickhouse-keeper.err.log | grep "RaftInstance\|Election"
```

#### 错误 4：Keeper 启动后 /clickhouse 路径为空

**原因**：snapshot 转换失败或未复制到其他节点。

**解决**：
```bash
# 1. 检查 snapshot 是否存在
ls -lh /data/clickhouse/coordination/snapshots/

# 2. 如果没有，重新转换
clickhouse keeper-converter \
  --zookeeper-logs-dir /home/yxpt/servers/zookeeper-3.7.2/zkData/version-2 \
  --zookeeper-snapshots-dir /home/yxpt/servers/zookeeper-3.7.2/zkData/version-2 \
  --output-dir /data/clickhouse/coordination/snapshots

# 3. 复制到其他节点
scp /data/clickhouse/coordination/snapshots/snapshot_*.bin.zstd root@15.28.140.42:/data/clickhouse/coordination/snapshots/
scp /data/clickhouse/coordination/snapshots/snapshot_*.bin.zstd root@15.28.140.43:/data/clickhouse/coordination/snapshots/

# 4. 重启 Keeper
systemctl restart clickhouse-keeper
```

#### 错误 5：clickhouse-backup create 失败 "mkdir: file exists"

**原因**：`/data/clickhouse/backup` 目录已存在（clickhouse-backup 期望它是软链接指向空目录）。

**解决**：
```bash
# 创建实际备份目录
mkdir -p /data/clickhouse/backup-data
# 将已有备份移走（如果有）
mv /data/clickhouse/backup /data/clickhouse/backup.bak 2>/dev/null || true
# 创建软链接
ln -sfn /data/clickhouse/backup-data /data/clickhouse/backup
# 重新运行 backup
clickhouse-backup -c /home/yxpt/ck/backup/clickhouse-backup/config.yml create <name>
```

#### 错误 6：RPM 升级 SHA256 digest BAD

**原因**：RPM 包签名校验失败。

**解决**：
```bash
rpm -Uvh --nodigest --nosignature <rpm-file>
```

#### 错误 7：CK 副本 is_readonly=1，absolute_delay 很大，无 exception

**原因**：Keeper 中没有这个副本的注册信息（可能从空 snapshot 启动）。

**解决**：
```sql
-- 在另一副本正常的节点执行
SYSTEM RESTART REPLICA <db>.<table>;
-- 或在 Keeper 中手动注册（极端情况）
```

### 3.2 Keeper 日志关键关键字

| 关键字 | 含义 | 严重程度 |
|--------|------|----------|
| `Election timeout` | 选主超时，可能网络问题 | 高 |
| `failed to connect to peer` | raft 节点不通 | 高 |
| `peer is busy` | 节点正常但负载高 | 低 |
| `total 1 nodes responded` | 多数节点未响应 | 高 |
| `KeeperTCPHandler: invalid four letter command` | 客户端用了非白名单命令 | 低 |
| `KeeperLogStore: Removing all changelogs` | 启动时清理损坏的 changelog | 中 |

### 3.3 ZooKeeper 日志关键字

| 关键字 | 含义 | 严重程度 |
|--------|------|----------|
| `No such file or directory`（启动时） | PID 文件不存在，重复启动 | 低 |
| `Cannot open channel to X` | 节点间网络不通 | 高 |
| `ZK startup complete` | 正常启动 | - |
| `is not in quorum` | 节点数不足，无法选主 | 高 |

## 四、最佳实践

### 4.1 备份策略

**clickhouse-backup 的正确理解**：
- `create`：freeze（硬链接）→ 打包 shadow/
- `restore`：解包 → 硬链接回原数据目录
- **备份期间不阻塞写入**，freeze 只是引用计数+1
- **restore 时才真正写盘**，需要足够的磁盘空间

**备份目录规划**：
```
/data/clickhouse/backup-data/     ← 实际备份存储（独立磁盘）
/data/clickhouse/backup -> /data/clickhouse/backup-data   ← 软链接
```

### 4.2 升级前检查清单

- [ ] `is_readonly=0` on all replicas
- [ ] `queue_size=0` on all replicas
- [ ] 无 pending mutations
- [ ] `absolute_delay=0` on all replicas
- [ ] 无 `last_queue_update_exception`
- [ ] 业务写入已停止
- [ ] 备份已完成且验证

### 4.3 Keeper 部署检查清单

- [ ] ZooKeeper 3 台全部停止
- [ ] snapshot 转换成功（有文件输出）
- [ ] snapshot 复制到全部 3 台节点
- [ ] Keeper 配置无 `<zookeeper>` 段
- [ ] Keeper raft 选主成功（1 leader + 2 follower）
- [ ] `system.zookeeper` 可查询 `/clickhouse` 数据
- [ ] metrika.xml 端口已修改（9181）
- [ ] CK 重启后 `is_readonly=0`

### 4.4 回滚决策树

```
CK 升级失败
├── 未恢复写入 → 降级 CK RPM + 恢复配置
└── 已恢复写入
    ├── 数据可重放 → 停止写入 + 降级
    └── 数据不可丢 → 保持 23.8 + 修复问题

Keeper 迁移失败
├── CK 23.8 正常 → 停 Keeper + 改回 2181 + 重启 CK
└── CK 也异常 → 降级 CK + 重启 ZK + 修复 Keeper
```

## 七、版本兼容性说明

| CK 版本 | Keeper 版本 | 兼容 | 说明 |
|--------|------------|------|------|
| 22.2 | 3.7.2 (ZK) | ✓ | 使用 ZooKeeper |
| 22.2 | 23.x (Keeper) | 未测试 | 可能不兼容，建议升级 CK 后再用 Keeper |
| 23.8 | 23.8 (Keeper) | ✓ | 同版本完全兼容 |
| 23.8 | 22.2 (ZK) | ✓ | CK 23.8 兼容 ZK 3.7 |

> 注：Keeper 23.x 使用 ZK 兼容协议，理论上支持连接 ZK 3.4/3.5/3.6/3.7。但建议 CK 和 Keeper 用同一版本。

## 八、监控建议

### 8.1 关键监控指标

**Keeper 端**：
- `zk_server_state`: leader/follower
- `zk_outstanding_requests`: 高值表示 Keeper 负载高
- `zk_znode_count`: 节点数量，突然变化需要关注
- `zk_num_alive_connections`: CK 连接数，应为 6（6 台 CK）

**CK 副本端**：
- `is_readonly`: 正常=0
- `absolute_delay`: 正常=0（秒）
- `queue_size`: 正常=0
- `inserts_in_queue`: 批量写入期间正常，完成后应为 0
- `merges_in_queue`: 有 merge 时正常，无 merge 时应为 0

### 8.2 告警规则

```yaml
# 建议 Prometheus 告警规则
- alert: ClickHouseReplicaReadonly
  expr: clickhouse_replicas_is_readonly > 0
  for: 5m
  labels: severity=critical
  annotations:
    summary: "CK 副本只读"
    description: "{{ $labels.host }} 上的 {{ $labels.table }} 处于只读状态"

- alert: KeeperNotLeader
  expr: clickhouse_keeper_state != "leader"
  for: 2m
  labels: severity=critical
  annotations:
    summary: "Keeper 无 leader"
    description: "所有 Keeper 都是 follower，无法选主"

- alert: ClickHouseReplicaQueueLarge
  expr: clickhouse_replicas_queue_size > 100
  for: 10m
  labels: severity=warning
  annotations:
    summary: "CK 副本队列积压"
    description: "{{ $labels.host }} 上的 {{ $labels.table }} 队列长度 {{ $value }}"
```
